Docs

Get started

OpenParley puts conversations on the elements of your live site: you point at what you mean, your teammates reply in the thread, and your coding agent picks it up, makes the change and replies too.

  1. Create a free workspace (or host your own).
  2. On its admin page, create a project for your site and list the origins where it runs: production, staging, http://localhost:5173.
  3. Paste the project's script tag into your site. By default it has data-launcher="members": only signed-in teammates load OpenParley (see On production). For a site only your team opens, the admin page can generate one for every visitor instead.
  4. Connect your coding agent and invite your team.

Then press C on your site, click an element and write. That's a thread.

Or let your coding agent set it up

Each project on your admin page has a Copy prompt button: a setup prompt with your workspace and project key filled in. Paste it into Claude Code, Cursor or Codex in your app's repository. The agent puts the script tag where your framework defines the page head, connects itself over MCP and adds a short section to your AGENTS.md, so later sessions know how to work through threads. It asks before it changes anything. The same prompt with placeholders is at /setup.md, and /llms.txt points agents at these docs as Markdown.

Let your coding agent answer threads (MCP)

With a workspace, a coding agent like Claude Code or Cursor can work through your threads: you click an element and write what should change, the agent finds the code from the thread's page, selector and element text, makes the change, replies with what it did and resolves the thread. You check it on the live element.

Add your server to the agent. The first time it connects, it opens your server in the browser so you can sign in and approve it:

claude mcp add --transport http openparley https://parley.example.com/mcp

In Claude Code, run /mcp and choose Authenticate. Other MCP clients: add https://parley.example.com/mcp as a remote server (Streamable HTTP); clients that support MCP's OAuth sign-in find everything else themselves. Then ask the agent to "work through the open OpenParley threads".

For an agent that can't sign in, create a token on the admin page under Agents instead. It's shown once, with the command: claude mcp add … --header "Authorization: Bearer opa_…".

So later sessions know about OpenParley without being told, add this to your repository's AGENTS.md (or CLAUDE.md):

{{AGENTS_SNIPPET}}
ToolWhat it does
list_threadsOpen threads (or resolved, or all), filtered by project or page, with URL, element and request
get_threadOne thread with the element's selector, text and attributes and the whole conversation
reply_to_threadReplies as the agent
resolve_thread, reopen_threadChanges the status, optionally with a reply

An agent acts for the person who connected it: its replies show the agent's name and "agent · your name". It can't start or delete threads or change anything on the server. Revoke it on the admin page at any time. Agents don't count as members. A signed-in agent stays signed in while it's in use; after 90 days without use it has to sign in again.

Bring your team

Product managers, designers, QA and anyone else who reviews the product use the same threads: they point at the real element instead of sending screenshots, and their feedback lands where the developer's agent can act on it. Agent replies are marked as the agent's, for the person who connected it.

On the admin page, enter a teammate's email under Members and press Invite. They get an email with a link (it works once, for 7 days); without an address, or on a server that doesn't send email, you get the link to send yourself. After they create their account, the admin page shows a link to each of your sites that switches OpenParley on in their browser, so it works even with data-launcher="members".

Members can comment, reply and resolve. Admins also manage projects, sites and members.

Mentions and notifications. Everyone has a mention name, like @mia, made from their name; change yours on the admin page. Type @ in a comment (or press the @ button) and pick a teammate; mentions are highlighted, yours in yellow. Agents can mention people by mention name or full name. On a server that sends email, people get an email when they're mentioned and when someone replies to or resolves a thread they started, wrote in or were mentioned in. Updates on a thread wait until it has been quiet for a minute and arrive as one email, and nobody is emailed about their own actions. Replies from a coding agent notify people too. Everyone chooses under Notifications on the admin page: nothing, only mentions, mentions and their threads (the default), or everything, for all projects or per project. Every email has a one-click unsubscribe link.

Self-hosting

The sync server is a single Bun process with a SQLite file. One server is one organization.

git clone https://github.com/openparley/openparley
cd openparley
bun install
bun run build                                  # builds the overlay the server hands out
PUBLIC_URL=https://parley.example.com bun apps/sync/src/main.ts

Or with Docker, from the same checkout, behind your reverse proxy. The database lives in the openparley volume.

docker build -f apps/sync/Dockerfile -t openparley-sync .
docker run -d -p 127.0.0.1:3001:3001 -v openparley:/data \
  -e PUBLIC_URL=https://parley.example.com -e TRUST_PROXY=1 openparley-sync
docker logs <container>                        # the setup link

On first start the server prints a one-time setup link. Open it to create the owner account. Then, on the admin page:

  1. Create a project and list the site origins where it runs, for example https://staging.example.com, or a wildcard such as https://*.preview.example.com for all subdomains. An admin can also add a site in one click from the sign-in window the first time they sign in there.
  2. Copy the project's script tag into those sites.
  3. Invite your team (PMs, designers, QA): by email, or copy the invite link. After accepting, they get a link to each site that switches OpenParley on for them.

Visitors see a Sign in button in the overlay. It opens a small window on your server; after signing in, the server sends a session token back to the page, but only if the page's origin is on the project's list. This list is what stops another site from copying your script tag and signing in your teammates: keep it to sites you run, and avoid wildcards on shared hosts like *.vercel.app, which include other people's sites.

Only for your team, on production

The script tag on your admin page has data-launcher="members" unless you chose Every visitor there:

<script src="https://parley.example.com/openparley.js" data-project="KEY" data-launcher="members" defer></script>
  • Visitors download a loader of under 1 KB, which checks a flag in their browser and stops. No overlay, no network requests.
  • A teammate switches it on once by visiting any page with #openparley at the end of the URL, or by opening a thread link a colleague shared, and signing in.
  • From then on, OpenParley loads in that browser on every visit. If the session expires, they see a Sign in button.
  • Sign out in the toolbar switches it off again, as does visiting with #openparley=off.

This controls who loads OpenParley, not who can read threads: that always requires signing in to your server. If your site can already tell employees apart, rendering the script tag only for them works too and costs customers nothing at all.

If your site sends a Content-Security-Policy, allow your OpenParley server in script-src and connect-src, and in font-src if you want the overlay in its own font (otherwise it uses the system font).

Script options

AttributeMeaning
data-projectProject key from your server. Turns on team mode.
data-serverServer URL. Defaults to wherever the script was loaded from.
data-launcher always (default) loads it for every visitor. members (team mode) loads it only in browsers where someone signed in to your server; see On production. auto (links only) loads it once someone opens a thread link or visits with #openparley, and keeps it on in that browser. #openparley=off switches members and auto off again.
data-shortcut Key that starts a new thread from anywhere on the page. Default c; any single key, or off.
data-shortcut-priority page (default): if the page handles the key itself, OpenParley ignores it. openparley: OpenParley handles the key first and the page never receives it.
data-environment Team mode. Threads show in the environment they were made in; by default each origin (production, staging, localhost) is its own. Give several origins the same label, e.g. preview on every preview deploy, to share their threads. Threads from other environments are listed under View all.
data-revision Team mode. Recorded on new threads, e.g. the deployed commit SHA, so a coding agent knows which code a thread was about.

Using it from code (coming soon)

The @openparley/overlay package isn't on npm yet. Until it is, use the script tag. Once published, it works like this:

import { mount } from '@openparley/overlay';

const overlay = mount({ project: 'abc123', server: 'https://parley.example.com', launcher: 'members' });
// later, e.g. when your app unmounts
overlay.destroy();

mount is safe to call more than once; it returns the existing instance.

Shortcuts never fire while you're typing in a field. C works anywhere; the others only while the overlay is open. If your site or app already uses C, OpenParley stays out of its way: when the page handles the key itself (it calls preventDefault() or stops the event), OpenParley ignores it. See data-shortcut to move or disable it.

How threads find their element

When you click an element, OpenParley records a CSS selector, its position in the page structure, its text, and identifying attributes such as id, data-testid and aria-label. On later visits it scores candidate elements against all of these. Small changes, like a renamed class or fixed typo, still match. If nothing matches convincingly, the thread shows as “element not found” in the list instead of being pinned to the wrong thing.

Tip: data-testid attributes and stable ids make anchors almost unbreakable. Threads belong to a page by its path; the query string doesn't matter. With a workspace they also belong to the environment they were made in (see data-environment).

Links and privacy

The conversation in a link is stored after the #. Browsers never send that part to the server, so it doesn't show up in your server logs or analytics. It is visible to anyone who has the link. Team-server links contain only an ID; the content stays on your server and needs a sign-in.

Anyone can craft a link that shows a thread on your site, as with any link-based tool. Comments are always shown as plain text, never as HTML or clickable links. On public production sites, use data-launcher="members" with a workspace, or data-launcher="auto".

Without a server

For a quick try or a one-off review, OpenParley also runs without any server. Threads stay in the browser and travel inside links; there are no accounts, no team and no agent access.

Build the overlay once and host the file next to your site:

git clone https://github.com/openparley/openparley
cd openparley
bun install
bun run build            # writes packages/overlay/dist/

Host every file in packages/overlay/dist together: openparley.js is a small loader that fetches openparley-app-<hash>.js from the same folder. Cache the app and font files forever (their names change with every release) and the loader briefly.

<script src="/openparley.js" defer></script>

Threads are saved in each visitor's browser (localStorage). Copy link on a thread produces a URL that contains the whole conversation. When someone opens it, the thread is added to their browser and opened on the element. If they reply, they copy a new link and send it back. Replies don't sync on their own; that's what a workspace is for.

Limitations

  • Desktop browsers only for now. Touch devices can view threads but picking elements is not tuned for them.
  • Sites that route with the URL hash (#/page) are treated as a single page.
  • Elements inside iframes and closed shadow DOM can't be picked individually.
  • OpenParley checks for new replies every 15 seconds and when you return to the tab, not instantly.
  • Notifications go by email only; Slack and Teams aren't supported yet.
